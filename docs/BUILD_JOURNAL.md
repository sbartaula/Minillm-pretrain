# Building Tenslam MiniLM From Scratch: A Technical Journal (Sessions 1 to 3 + GPU Benchmark)

*Written for listening: it is mostly prose, with the numbers and reasons spelled out. Everything below is
taken from the real code, configs, manifests and benchmark in this repository. Where something is an
assumption or still unknown, it is said explicitly.*

---

## 1. What we are building, and why

Tenslam MiniLM is a small language model written from scratch. "From scratch" means:

- **No pretrained weights.** Every parameter starts as random noise and learns only from our data.
- **Our own architecture code.** The Transformer is about 175 lines of plain PyTorch, not a wrapper around Hugging Face `transformers`.
- **Our own tokenizer**, trained by us on our training data only.
- **Our own training loop**, checkpointing, evaluation and cost estimator.

The goal is education and a portfolio-quality project. The model has about **30 million parameters**, a tiny model by
modern standards (GPT-2 small is 124M, modern chat models are billions). It is trained on **TinyStories**, a dataset of
simple short stories written for small children. The point is to understand every moving part, not to compete with
big models.

Hard constraints we set at the start:

- No downloading pretrained models.
- Validation data must be the official validation split, never mixed with training data.
- Everything must be reproducible: pinned data version, fixed seeds, recorded hashes.
- Never start a paid GPU without explicit approval. Total GPU budget at most 8 euro.

## 2. The data

### Where it comes from

The dataset is `roneneldan/TinyStories` on Hugging Face. It was generated by GPT-3.5 and GPT-4 following prompts
that restrict vocabulary to what a 3 to 4 year old would understand. The license is `cdla-sharing-1.0`.

**Why TinyStories?** Research from the TinyStories paper showed that even very small models (millions of
parameters) can produce coherent English stories when the data is simple and narrow. A 30M model trained on
Wikipedia would produce mush. Trained on TinyStories it can produce readable stories. That makes it the best
dataset for a small model, a small budget and a short time. It also has an official train/validation split, which we
need for honest evaluation.

**Alternatives we did not use:**

- *OpenWebText / FineWeb / Wikipedia:* far larger and messier. A 30M model would not learn useful English from a
  small slice, and cleaning would dominate the project.
- *Shakespeare / tiny character-level data:* fine for demos, but a poor portfolio story and too little data.
- *Synthetic data we generate ourselves:* would need an LLM API, which costs money and adds a dependency on
  someone else's model, against the "no pretrained" spirit.

### Pinning the version

In `configs/data.toml` the dataset is pinned to a specific git commit (`revision = f54c09fd...`). Datasets on Hugging
Face can change; pinning means the same bytes arrive every time. Every manifest records this revision.

### Streaming and sampling

We do not download the whole dataset (several GB). We use Hugging Face **streaming** with a **seeded shuffle buffer**
(buffer 10,000 rows, seed 1337 for train, 1338 for validation) and take the first N rows. This gives a roughly random
sample without a full download. The trade-off: a shuffle buffer is not a perfectly uniform shuffle, but it is good
enough, and it is deterministic given the seed.

Sizes used:

- Session 1 (tokenizer and sanity work): 10,000 train stories, 1,000 validation.
- Session 3 local development: 50,000 train, 1,000 validation.
- **RunPod run: 600,000 train stories requested, 5,000 validation requested.**

### Cleaning (`preprocess.py`)

Every story goes through deterministic filtering. Deterministic means same input, same output, always.

1. **Unicode normalization to NFC.** The same visible character can be stored as different byte sequences (for
   example "é" as one code point or as "e" plus a combining accent). NFC picks one canonical form, so identical text
   is byte-identical. In the RunPod run 219,950 of 600,000 train stories were modified by normalization, mostly
   typographic quotes and similar.
2. **Mojibake repair.** Mojibake is garbled text from encoding mistakes, like "â€™" instead of an apostrophe. We
   try to repair it. If it cannot be repaired the story is dropped (29 stories).
3. **Length filter.** Stories under 50 characters or over 10,000 characters are dropped. Empty ones (78) and too-short
   ones (2) were removed. Total invalid in the RunPod train set: 109.
4. **Exact deduplication.** After normalization, identical stories are removed. We found **25,959 duplicates among
   600,000** (4.3%). Duplicates matter because a model memorizes repeated text and the validation loss then looks
   better than it should.

**Why exact dedup and not fuzzy dedup (MinHash, near-duplicates)?** Exact dedup is simple, fast, provable and
explainable. Fuzzy dedup is better for web-scale data but adds complexity and tuning. For this project exact is
enough; fuzzy is a possible later improvement.

### Train and validation must not overlap

This is the most important integrity rule. If validation stories also appear in training, the model is being tested on
things it memorized, and the validation loss is a lie (data leakage).

In `prepare.py` we remove from validation anything whose **loose key** matches a training story. The loose key is a
normalized form: lowercased and whitespace-collapsed, so tiny formatting differences do not hide a match. Then the code
**asserts** that the overlap is empty and crashes if it is not. In the RunPod run, 76 validation stories were removed
for matching training, and 76 more were exact duplicates inside validation itself.

### Final dataset sizes (RunPod run)

- Train: 600,000 raw, **573,932 kept**, **125,952,650 tokens**, about 219 tokens per story.
- Validation: 5,000 raw, **4,924 kept**, **992,483 tokens**.
- Stored as `train.bin` (about 241 MB) and `validation.bin` (about 1.9 MB), plus `prepare_manifest.json`.

The manifest records SHA-256 hashes of the raw files and the tokenizer, the library versions, the seeds, the
preprocessing config, the dataset revision and token counts. **The trainer re-verifies the hash of the token files
before training.** That check is why a corrupted upload (which happened repeatedly, see section 9) cannot
silently poison a training run.

## 3. The tokenizer

### What a tokenizer does

A neural network only understands numbers. A tokenizer converts text to integer ids and back. The model never sees
letters, only ids, and learns a vector (an embedding) for each id.

### What we chose: byte-level BPE with 8,192 tokens

- **BPE (Byte Pair Encoding):** start from individual symbols, then repeatedly merge the most frequent adjacent
  pair into a new token. After 8,000 or so merges, common words like "the" or "little" become single tokens, while
  rare words split into pieces.
- **Byte-level (GPT-2 style):** the base alphabet is the 256 possible bytes. So any string, even emoji or a typo,
  can be encoded. There is **no unknown token**. Nothing can ever fall outside the vocabulary.
- **Regex pre-split:** text is first split into word-like chunks, so merges never cross word boundaries.
- **Trained on the training sample only.** If the tokenizer saw validation text, that would be a subtle leak.
- **Special tokens:** `<|pad|>` id 0, `<|bos|>` id 1, `<|endoftext|>` id 2 (our EOS, which separates documents).

### Why 8,192 and not 50,000?

This is a key trade-off. The embedding matrix has `vocab_size x d_model` numbers. With d_model 512:

- 8,192 tokens gives 4.2 million parameters in embeddings (14% of the model).
- 50,257 tokens (GPT-2) would give 25.7 million parameters, nearly the whole budget, just for embeddings.

TinyStories uses a very small vocabulary of words, so 8k tokens cover it well. A smaller vocabulary also means a
cheaper softmax at the output (the model scores all 8,192 tokens at every position). 8,192 is also a multiple of
64, which is GPU-friendly. The cost: fewer characters per token, so sequences are a bit longer. For simple
children's English that cost is small.

Also, token ids stay under 65,536, so we can store them as `uint16` (2 bytes per token). That is why
126M tokens take about 252 MB.

### Alternatives we did not use

- **Character-level:** tiny vocabulary, but sequences become very long and the model wastes capacity learning spelling.
- **Word-level:** needs an unknown token and huge vocabulary; cannot handle new words.
- **WordPiece / Unigram (SentencePiece):** also valid. BPE is the simplest to explain and matches GPT-style models.
- **Reusing GPT-2's tokenizer:** the quickest option, but it would be someone else's artifact, and its 50k vocabulary is
  too expensive for a 30M model.

## 4. The model architecture

A **decoder-only Transformer** in the LLaMA style. It has 8 layers, `d_model` 512, 8 attention heads (head size 64),
SwiGLU hidden size 1,408, context length 512, and tied embeddings. Total: **29,893,120 parameters**.

Where the parameters go, roughly:

- Embeddings: 8,192 x 512 = 4.2M (shared with the output layer, see tying below).
- Per layer: attention 4 x 512 x 512 = 1.05M, SwiGLU 3 x 512 x 1,408 = 2.16M, so about 3.2M.
- Eight layers: about 25.7M. Plus embeddings gives about 29.9M.

### The data flow

Token ids go through an embedding lookup, then 8 blocks, then a final normalization, then a linear layer that
produces a score (logit) for each of the 8,192 possible next tokens.

Each block is:

```
x = x + Attention( RMSNorm(x) )
x = x + SwiGLU( RMSNorm(x) )
```

Two ideas appear here:

- **Residual connections** (`x = x + ...`): each layer adds a correction to a running "stream" instead of replacing it.
  This lets gradients flow through deep networks.
- **Pre-norm:** normalize before each sub-layer, not after. This trains more stably than the original 2017
  post-norm design.

### Component by component

**Causal self-attention.** For each token, attention computes how much to look at every earlier token. Every token
produces a query (Q), key (K) and value (V). The attention output is
`softmax(Q K^T / sqrt(d)) V`. The `1/sqrt(d)` scale keeps the dot products from growing with head size, which would
make the softmax saturate. The **causal mask** forbids looking at future tokens, because the task is to predict the
next token and looking ahead would be cheating. We use PyTorch's fused `scaled_dot_product_attention` with
`is_causal=True`, which uses FlashAttention-style kernels on GPU (fast, and it never builds the full attention
matrix in memory). We tested that changing a future token never changes earlier outputs.

**RoPE (rotary position embeddings).** Attention alone has no notion of order. RoPE injects position by rotating
pairs of dimensions in Q and K by an angle that depends on the position. The dot product between two rotated vectors
then depends on their **relative distance**. Alternatives: *learned absolute positions* (GPT-2; cannot extrapolate
and add parameters), *sinusoidal* (original Transformer; works but older), *ALiBi* (a bias on attention scores).
RoPE is what LLaMA and most modern models use, and it adds zero parameters.

**RMSNorm.** `y = x / sqrt(mean(x^2) + eps) * g`. It is LayerNorm without the mean subtraction and bias, so it is
cheaper and works equally well. We compute it in float32 even when the rest runs in bf16, for numerical safety.

**SwiGLU.** The feed-forward block is `down( silu(gate(x)) * up(x) )`. The gate learns what information to let
through. It uses three matrices instead of two, so the hidden width is shrunk to about 8/3 x d_model (1,365,
rounded to 1,408 for GPU-friendly shapes) to keep parameters comparable to a classic MLP. It consistently beats plain
GELU MLPs at equal parameter count.

**No bias terms anywhere.** Fewer parameters, simpler, no measurable loss in quality at this scale.

**Weight tying.** The input embedding matrix and the output projection are the **same matrix**. Intuition: the vector
for "cat" going in and the direction scored for "cat" coming out should be related. It saves 4.2M parameters, which is
14% of the model, and tends to help small models. We have a test that confirms the tie survives saving and loading
checkpoints.

**Initialization.** Weights start from a normal distribution with std 0.02. The output projections of attention and
SwiGLU (the layers that write into the residual stream) are shrunk by `1/sqrt(2 x n_layers)`, the GPT-2 trick. Each
block adds two contributions to the stream, so without scaling, the variance of the stream would grow with depth.

**Loss.** Cross-entropy between the predicted distribution and the true next token, computed in float32.
At initialization, with 8,192 tokens, the expected loss is `ln(8192) = 9.01`. We observed about 9.0 at the start of
every run, which is a nice sanity check that nothing is broken. **Perplexity** is `exp(loss)`: roughly "how many tokens
the model is hesitating between".

### Why this size and shape

At 30M parameters, 8 layers and width 512 is a balanced, deep-enough shape. Our dataset has about 126M tokens. A
common rule of thumb (Chinchilla) says to train on roughly 20 tokens per parameter for compute-optimal training, which
would be about 600M tokens for 30M parameters. For TinyStories, models learn well with fewer. That is one reason
the next decision is about how many tokens to train on.

### What we verified before any real training (Session 2)

- Forward pass shapes are right; backward pass produces finite gradients for every parameter.
- The causal mask truly blocks the future (tested by changing future tokens).
- **One-batch overfit test:** train on a single batch repeatedly. Loss went from about 9.0 to 0.0001. If a model cannot
  memorize one batch, something is broken. It can, so the forward, backward and optimizer are correct.
- 55 tests passing at that point.

## 5. Turning text into training examples

### Binary token storage

All documents are tokenized, and an **EOS token (id 2) is appended after every story**. Then everything is
concatenated into one long array of `uint16` values and written to a `.bin` file. At train time the file is opened with
`np.memmap`, a memory-mapped array: the operating system loads only the pages we touch, so even a huge file uses
almost no RAM.

### Sampling and shifted targets

For each training example, we pick a random start position `s` and take `seq_len + 1 = 513` consecutive tokens:

```
window  = tokens[s : s+513]
input   = window[0:512]      # what the model sees
target  = window[1:513]      # what it must predict
```

Target position `t` equals input position `t+1`, so at every position the model predicts the next token. One
window therefore gives **512 training signals**, not one. We have a test for this alignment, since an off-by-one here
would silently ruin training.

### Packing, EOS and document boundaries

Windows are cut from the continuous stream, so one window may contain the end of one story, the EOS token, and the
start of the next. The model sees `... the end. <EOS> Once upon a time ...`.

- **Loss does cross document boundaries.** The model is also trained to predict the first token of the next story after
  an EOS, and the attention can see across the boundary. We did not mask it.
- **Why we accepted that:** it is the standard approach (GPT-2, GPT-3, nanoGPT). The EOS token tells the model "a new,
  unrelated story starts". Masking attention at document boundaries is cleaner but more complex, and for this setting
  the effect is small. The choice is documented in the README.
- **Why EOS is essential:** it lets the model learn when a story ends, and lets us stop text generation properly.

### Sampling is deterministic

Each batch is drawn with `np.random.default_rng([seed, step, micro])`. The random choice is a pure function of the
seed, the optimizer step and the micro-batch index. This means:

- A run is exactly reproducible.
- After resuming from a checkpoint, the data stream continues exactly where it would have, with no repeated or
  skipped batches.

Sampling is with replacement (random windows), not epochs of shuffled data. That is common in LLM pretraining and
makes "tokens processed" the natural unit instead of "epochs".

### Validation sampling

Validation is the opposite: **fixed, non-overlapping consecutive windows** in order, with no randomness. Every
evaluation looks at the same text, so changes in validation loss reflect the model changing, not the sample changing.

## 6. The training engine (Session 3)

Everything is in `train.py`, `schedule.py`, `checkpoint.py` and `generate.py`.

### Optimizer: AdamW

Adam keeps a running average of the gradient (momentum, `beta1 = 0.9`) and of its square (`beta2 = 0.95`), and scales
each parameter's update by the inverse of the typical gradient size. That adaptivity is why it works well for
Transformers. **AdamW** applies **decoupled weight decay**: instead of adding L2 into the gradient, it shrinks weights
directly each step. We use weight decay 0.1 on matrices only, and **not on norm gains**, which are 1D and should not be
pulled toward zero. `beta2 = 0.95` (instead of the default 0.999) is the usual choice for LLM training because it adapts
faster.

*Alternatives:* SGD (poor for Transformers), Adafactor and Lion (memory-saving, unnecessary at 30M), Muon (newer
and interesting, a possible future experiment).

### Learning-rate schedule: warmup then cosine decay

- **Warmup** (150 steps): the learning rate rises linearly from near zero to the peak 1e-3. At the start, Adam's
  statistics are unreliable and the weights are random, so a large step could destabilize everything.
- **Cosine decay**: the rate falls smoothly following half a cosine wave from 1e-3 down to a floor of 1e-4.
  Formula: `lr = min + 0.5 x (peak - min) x (1 + cos(pi x progress))`.
- A small detail: at step 0 the rate is `peak x 1/warmup`, never exactly zero.

The schedule is a pure function, so it is easy to test and easy to resume.

### Gradient accumulation

We want a large batch for stable gradients, but a GPU only has so much memory. So we run several **micro-batches**,
add up their gradients, and take one optimizer step. Each micro-loss is divided by the number of accumulation steps
so the sum equals the average. We test that accumulating 4 micro-batches gives the same gradients as one big batch.

RunPod config: micro-batch 32, accumulation 4, sequence 512, so **65,536 tokens per optimizer step**
(32 x 4 x 512).

### Gradient clipping and stability checks

- **Clipping:** before each step, if the global gradient norm exceeds 1.0 it is scaled down. One bad batch cannot blow
  up the model.
- **Non-finite checks:** if the loss becomes NaN or infinity, or parameters contain NaN or Inf, training stops safely
  (`NonFiniteError`) and does not continue from a corrupted state. Tested.

### Mixed precision

Training in 32-bit floats is slow. GPUs have fast 16-bit hardware, and there are two 16-bit formats:

- **bf16 (bfloat16):** same range as float32, less precision. No scaling needed. Requires newer GPUs (compute
  capability 8.0+).
- **fp16:** more precision, small range, so tiny gradients can underflow to zero. It needs a **GradScaler**: multiply
  the loss by a large number before backward, then divide gradients before the step, and skip the step if there are
  infinities.

The code chooses automatically: bf16 on modern GPUs, fp16 with a GradScaler on older ones (like Kaggle's T4), and plain
fp32 on CPU. The RTX A5000 we rented picked **bf16 with no scaler**. Master weights and the optimizer stay in fp32;
only the forward and backward compute is in bf16 (autocast).

### Evaluation

Every 250 steps we run validation under `model.eval()` and `torch.no_grad()` (no dropout behaviour, no gradient
tracking, so weights never change). A test confirms evaluation does not alter the weights. We log validation loss and
perplexity.

### Logging

Each logged step records learning rate, tokens processed, step time, gradient norm and tokens per second into a
structured metrics file (JSONL/CSV). Every 500 steps the model also generates text from fixed prompts (for example "Once
upon a time, there was a little girl named"), so you can literally watch it learn: first gibberish, then words, then
sentences, then stories.

### Checkpointing and recovery

A **resumable checkpoint** saves everything needed to continue as if nothing happened: model weights, optimizer
state (Adam's running averages, as large as the model itself), scheduler state, scaler state, global step, tokens
processed, **Python, NumPy and PyTorch RNG states**, the config, and the tokenizer hash. Writes are **atomic**: write to
a temp file, then rename, so a crash mid-write can never leave a half-written corrupt checkpoint.

A separate **inference-only export** contains just weights and config. It is smaller (no optimizer state) and is
what you would publish. A resume test verifies that stopping and resuming reproduces the same training.

A checkpoint is about **359 MB** and took **0.27 seconds** to save on the rented GPU.

### Controlled stops

Training supports a **maximum token budget** and a **maximum wall-clock time**. When the limit is hit, or on Ctrl-C,
it saves a checkpoint and exits cleanly. This protects against runaway spending. The RunPod config has a 0.5-hour
safety cap.

### Device handling

The same code runs on CPU or CUDA with no source changes (`device = "auto"`). A CUDA-only test is skipped on the laptop
(that is the "1 skipped" in the test summary).

### Testing summary

At the end of Session 3 the suite had **88 passed, 1 skipped**. It covers: next-token alignment, EOS handling,
train/validation separation, deterministic sampling, gradient accumulation, scheduler shape, checkpoint round-trip,
weight tying after load, evaluation without updates, device selection, and NaN detection.

A CPU smoke test (tiny model, 60 steps) took validation loss from 8.99 to 5.24 and resumed correctly from a
checkpoint.

## 8. The GPU benchmark: real measurements

We chose **RunPod** over Kaggle (Kaggle is free and remains a documented fallback, but it has session limits and
older GPUs). We rented one **RTX A5000 (24 GB)** at about $0.27 per hour on a PyTorch 2.8 / CUDA 12.8 template with no
persistent storage, because this was benchmark-only.

Measured on the real GPU (10 timed steps after 3 warmup steps), bf16, sequence 512:

| Micro-batch | Tokens per second | Peak VRAM |
|---|---|---|
| 16 | about 140,600 | 3.3 GB |
| 32 | about 148,200 | 6.3 GB |
| 64 | about 153,100 | 12.1 GB |

**Reading these numbers:**

- Throughput barely grows with batch size beyond 32, meaning the GPU is already saturated. A bigger batch buys memory
  use, not speed.
- All losses were finite, and the loss went from 9.08 to about 7.6 in 13 steps. That only proves the loop works, it says
  nothing about final quality.
- Validation pass: 1.8 to 3.5 seconds. Checkpoint save: 0.27 s. A text sample: about 2 s. These overheads are tiny.
- We did **not** use `torch.compile` (`compile = false`), so there may be extra speed available later.

**Estimated cost (at an assumed 0.25 euro per hour, including an assumed 15 minutes of setup):**

| Training tokens | Training time | Total with setup | Cost |
|---|---|---|---|
| 10M | about 1 min | 0.27 h | about 0.07 euro |
| 50M | about 5.5 min | 0.34 h | about 0.09 euro |
| 100M | about 11 min | 0.44 h | about 0.11 euro |
| 200M | about 22 min | 0.62 h | about 0.16 euro |

**Caveats, stated honestly:** setup time is an assumption, throughput comes from only 10 timed steps, the dollar to
euro conversion is rough, and storage or data-transfer fees are not included. Even if the real numbers are several
times worse, the 8 euro budget is far from threatened. Compute is not the bottleneck.

We stopped and terminated the pod after saving `benchmark_cuda.json` locally. Nothing paid is running.

## 9. Mistakes and lessons (worth remembering)

1. **Large browser uploads silently truncated** (JupyterLab cut files at around 56 MB and 20 MB). The tool gave no
   error. We caught it with `unzip -t` (integrity test) and file sizes. Lesson: always verify size and a checksum
   after transfer. For big files, split into small pieces (`split` then `cat`) and compare a SHA-256 hash.
2. **Deleting the wrong thing:** running `rm -rf` on the folder that held already-extracted data forced a re-upload.
   Lesson: never delete before you have verified the replacement.
3. **A hash check in the trainer** is the safety net that makes data corruption loud instead of silent.
4. **Local shell quirk:** a ROS installation leaks `PYTHONPATH` and breaks pytest, so we `unset PYTHONPATH`.
5. **Hugging Face streaming** crashes harmlessly at interpreter shutdown, so the prepare command flushes and exits with
   `os._exit(0)`.

- Option B: prepare more TinyStories (the full dataset is on the order of 450M tokens) and train 300M to

Because the GPU is so cheap relative to budget, Option B is probably the best use of the project. A cleaner way to avoid

check that the prepare step runs there.

**Decision 2: hyperparameters.** Peak learning rate 1e-3 with floor 1e-4 and warmup 150 is a reasonable start for a
30M model. Micro-batch 32 with accumulation 4 (65k tokens per step) is sound. Larger batches (131k) are fine too.

**Then the Session 4 plan:**

## 12. Glossary (for listening)

- **Token:** an integer id for a piece of text.
- **Embedding:** a learned vector for each token id.
- **Logit:** a raw score before softmax; one per vocabulary item.
- **Cross-entropy loss:** how surprised the model is by the true next token; lower is better.
- **Perplexity:** `exp(loss)`; the effective number of choices the model hesitates between.
- **Epoch:** one pass over the training data.
- **Micro-batch / accumulation:** splitting one big batch into pieces that fit in memory.
- **VRAM:** the GPU's own memory.
- **bf16 / fp16:** 16-bit number formats for fast training.
- **Residual stream:** the running vector that each layer adds to.
- **Causal mask:** forbids a token from seeing later tokens.
- **Memory-map:** reading a file as if it were an array without loading it all into RAM.
- **Atomic write:** write to a temp file then rename, so the result is all-or-nothing.
